# Evidence guide: where evidence lives in a PR package

## Plan fidelity (harness category: silent-drift)

Where it lives: in a practice submission (for example `eval/packages/calib-01.md`), the plan is under `## Plan context`: the `Plan:` paragraph gives the change, the `Files:` line, the `Not in scope:` line, and any deviation note. The change itself is under `## Candidate PR` → `### Diff`, one hunk per `@@` header with its file in the `---`/`+++` lines, and `### Commits` lists the commit messages. The description's fidelity claims are under `### Description`. Live, the plan is your `plan.md` (deviation notes included), the change is the output of `git diff main...HEAD` run from the working copy, the commits are `git log main..HEAD --oneline`, and the description is your `pr_draft.md`.

What good looks like: every hunk lands in a file or area the plan names, or in a test or record for the planned change, or is covered by a deviation note. Every planned change appears in the diff or is explicitly deferred. Calib-01 is the anchor: the plan names `themes.gitconfig` and one line removal, and the diff is exactly that one line. Silent drift goes in either direction. calib-03 adds a second hunk rewriting `print/property.js`, a file the plan never touches, under a description claiming "no changes beyond the plan". pkg-17 promises a docs update the diff never contains while the description claims the docs "now document the limitation". A description claiming more or less than the diff delivers is drift, not a comms problem.

## Test evidence (harness category: not-tested)

Where it lives: in a practice submission, `### Test evidence` under `## Candidate PR` (sometimes with before/after blocks in `### Description`), read against the `Test plan:` line and the `Repro evidence` paragraph under `## Plan context`. The repo's own check commands come from the `## Repo facts` block. Live, it's your `test_evidence.md`: the output of `make test-unit`, `make test-integration`, `make lint`, and `make typecheck`, plus your Unit 2 repro steps re-run on `main` (before) and on your branch (after). Read it against the test plan in your `plan.md` and the PR template's check list.

What good looks like: the evidence re-runs the plan's repro on the failing path with the same inputs, shows an observable after (an output, exit code, or rendered result) next to the before, and covers every failure mode the test plan names. The repo's own checks are shown with their outcomes. A failing or unrunnable check reported honestly with its reason still counts, such as Path Review's `make test-integration` stopping with "no tests ran". Calib-01 passes: the strict configparser re-run shows the before error and the after "parsed OK". It fails when the evidence is "tested locally, colors work now" (pkg-04), exercises only the single-file control (pkg-07) or the unchanged GET path (pkg-14), or never mentions one of the two failure modes the plan named (calib-04). A secondary failure mode addressed with a stated result passes: pkg-05 shows the issue script's before and after tables, then states that a same-key redefine prints the one-time warning.

## Diff quality (harness category: unreviewable)

Where it lives: in a practice submission, every `+` and `-` line under `### Diff` and every message under `### Commits`. Live, the full `git diff main...HEAD` and `git log main..HEAD --oneline`.

What good looks like: every changed line is the fix, its test, or a record the repo asks for, and the commit messages describe the fix. The debris tells are debug output left in (`eprintln!("DEBUG`, `console.log`, `print(`), commented-out code or an earlier attempt, dead functions (a `_unused_` name or `#[allow(dead_code)]`), stray TODOs, re-indent or whitespace-only hunks, identical lines removed and re-added, and import reshuffles the fix doesn't need. Lines removed and re-added identically count as churn when a whole block is re-printed with no change (pkg-18's `println!` blocks). They don't count when they belong to a statement that has a real change (pkg-02's multi-line `export_html(` call, where only `clear=` changed). Commit messages like "wip", "fmt + cleanup", or "misc cleanups while debugging" usually point at debris. pkg-12, pkg-15, and pkg-18 each carry a correct fix buried under these.

## Standards and comms (harness category: standards-wall)

Where it lives: in a practice submission, the repo's asks are under `## Repo facts`. The `pull requests:` line names the template sections, checklist items, and required files (changelog, whatsnew, closes #N). The `contribution policy:` line names any AI-use policy. The PR's compliance is in `### Title`, `### Description`, and (for required files) `### Diff`. Live, the asks are in the repo's `.github/pull_request_template.md` and `docs/CONTRIBUTING.md` (fetch them from the scoped repo or read them from your working copy). Compliance is in your `pr_draft.md` title and description.

What good looks like: every stated template section is present with real content, every required checklist item is answered, the issue-link line is there when asked for, and any required changelog or whatsnew file appears in the diff. When the repo states an AI policy that asks for disclosure, the description discloses the assistance in the author's own words. Treat every package as AI-assisted. pkg-11 satisfies ripgrep's policy with a one-sentence human-in-the-loop disclosure. pkg-08 answers each lazygit checklist item in one line. It fails when pandas' required checklist and whatsnew entry are visibly absent (pkg-01), or when ghostty's policy requires disclosing all AI use and the description has none (pkg-20). A repo with no template and no AI policy passes these checks vacuously. Whether the description's claims match the diff is plan fidelity, not this family.
