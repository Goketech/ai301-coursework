# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-cause | The plan's stated cause read against the repro-evidence block's Steps, Controls, and Artifacts | Pass if the stated cause cites behavior the repro evidence actually shows and contradicts no control run in the package; fail if it blames a mechanism a control rules out or ignores the evidence's pinned behavior. A terse cause that fits every control passes. | required |
| bounded-scope | The plan's in-scope change plus Files or areas read against the issue's observed failure and the repro evidence | Pass if every committed change serves the observed failure and anything beyond it is explicitly deferred or out of scope; fail if the plan commits to building a migration, refactor, redesign, new feature, or cross-area rework the issue never asked for, even when the core fix inside it is correct. Stated deferrals with reasons pass. | required |
| executable | The plan's Files or areas plus Approach read as a stranger's starting instructions | Pass if a stranger can start without asking the author anything: at least one concrete file or area plus one chosen approach in a workable order. Fail if no files and no chosen approach are named, or every real decision is deferred to build time. Notes flagged for review rather than built pass. | required |
| decisive-test | The plan's Test plan read against the repro evidence's Steps, Artifacts, and Expected outcome | Pass if the test re-runs the repro's pinned steps or fixture and names the observable artifact that proves the fix plus the controls that must stay unchanged. Fail if the test names no observable outcome for the fix itself, such as feel-based language, nothing-broke language, or a full-suite run alone. | required |
| honest-unknowns | Risk, unknown, and certainty claims in the plan read against what the repro evidence and thread actually establish | Pass if open questions, unverified support, unmeasured costs, and deviations are stated as such and left for review or follow-up. Fail if the plan asserts as fact what the evidence marks uncertain, claims verification it never ran, or dresses a guess as a traced result. | required |
| thread-engagement | The plan plus the plan comment read against the Thread highlights' maintainer signals | Pass if the package engages any explicit maintainer direction present in the thread (a named culprit, a posted test binary with a testing request, prior-art PRs, or listed fix options) by following it, deferring it with reasons, or rebasing onto it; pass vacuously when the thread states no direction. Fail if explicit direction exists and neither the plan nor the comment mentions it, such as a docs-only workaround over an isolated code culprit. | required |
| convention-disclosure | The plan comment read against the repo-facts block's stated templates, contributing asks, and AI-use policy | Pass if the comment satisfies what the repo-facts block actually states, including any AI-assistance disclosure and any human-words comment rule. Fail if a stated disclosure or comment rule is omitted or violated. Pass vacuously when the repo states no AI or comment policy. Silence on optional template fields never fails this check. | required |
| comment-ready | The plan comment read alone as the maintainer's first impression | Pass if the comment leads with the repro outcome, sketches the planned change, and names the next step without boilerplate or hype. Fail only on vague enthusiasm with no evidence and no plan content. | preferred |

## Verdict rule

Accept if and only if every required check passes. Preferred checks never change the verdict; they are signal for the summary only. An unclear grade counts as fail: a check that cannot be verified from the package text is a package that is not ready to build from. Every fail and every unclear on a required check yields reject; otherwise accept.
